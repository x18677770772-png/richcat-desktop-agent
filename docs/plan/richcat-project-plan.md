## 一、执行摘要

**RichCat（财听猫）是一款纯视觉驱动的 AI 微信客服桌面系统**——不看协议、不碰接口，像真人一样"看"微信窗口：识别未读、理解意图、自动回复、建档客户、沉淀记忆。v1.1.0 已具备 F1–F10 全套工业级功能并通过 QA 验收。

本规划的核心判断：

> **RichCat 的独特生态位 = 个人号 × 群聊 × 视觉 × 全流程。** 在 2026 年微信客服赛道里，官方 iLink 协议合规但只能 1v1、不能群聊；WeChatFerry 已停更；企微官方 API 面向企业但门槛高。**"个人微信 + 群聊场景 + 合规零封号"同时成立的方案，视觉路线几乎是唯一选择**——而 RichCat 是这个生态位里唯一把"客服闭环"（CRM/知识库/人设/日报/接管）做完整的开源产品。

**12 个月三阶段目标：**

| 阶段 | 时间 | 主题 | 里程碑产出 |
|---|---|---|---|
| **A 根基** | 2026-08 ~ 11 | Learn 落地 + 工程化 | v1.2.0（Learn 闭环） |
| **B 落地** | 2026-11 ~ 2027-05 | 任务层 + 达人建联垂直场景 + 商业化雏形 | v2.0（任务引擎）+ 达人建联工作台 |
| **C 破圈** | 2027-05 ~ 08 | 开放标准 + 组织记忆服务 + 生态 | work-trace 规范 + 企业版 MVP |

**三句话策略：**
1. 用**开源**建立影响力，把"工作记忆引擎"讲成行业第一的差异化故事；
2. 用**达人建联垂直场景**做第一个"学了再干、干完更会"的付费闭环；
3. 用**开放 trace 标准 + 组织记忆服务**筑起企业级护城河。

## 二、项目定位与愿景

### 2.1 是什么 / 不是什么

| | 说明 |
|---|---|
| ✅ 是 | 个人/小团队的 AI 微信客服值守：自动回复 + 客户档案 + 知识库 + 人设 + 全套客服运营能力 |
| ✅ 是 | 纯视觉 RPA 引擎：适配微信/企微/钉钉/飞书等任意桌面应用，零接口依赖 |
| ✅ 是 | 本地优先的工作记忆引擎：每次执行留痕、可回放、可评测、可继承 |
| ❌ 不是 | 微信协议注入/逆向工具（无封号风险，但速度与规模上限低于协议方案） |
| ❌ 不是 | 云 SaaS（数据全在本地，>后续企业版才上服务端，且自托管） |

### 2.2 目标用户与核心痛点

| 用户群 | 痛点 | RichCat 的价值 |
|---|---|---|
| **微信卖货的个人/小团队**（微商、私域店主、代购、个体） | 消息多、回复慢、重复问题多、客户记不住 | 7×24 值守 + 客户自动建档 + 知识库兜底 |
| **达人建联/商务 BD**（MCN、品牌、广告） | 批量触达达人、多轮跟进、话术沉淀 | 任务层批量触达 + 建联策略卡（Phase B） |
| **企微/钉钉等内的工作组**（销售/售后/专家） | 群内分工、VIP 差异化、服务日报 | F1/F3/F4 群聊与角色路由 |
| **开源开发者 / 研究者** | 桌面 GUI Agent 无标准、无中文语料 | work-trace 规范 + 中文企业软件轨迹语料（Phase C） |

### 2.3 核心价值主张（一句话）

> **让 AI 像真人客服一样，7×24 在微信上值守你的生意——不依赖任何微信接口，纯视觉，纯本地，越用越懂你的业务。**

### 2.4 护城河

1. **生态位独占**：个人号+群聊+合规，视觉路线内唯一完整客服闭环（详见 §3）。
2. **过程性记忆**：Mem0/Letta 等都在做"对话事实记忆"，没人做"为什么这么操作"的过程记忆（点击依据、失败模式、人工接管）。这是行业空白。
3. **中文企业场景语料**：微信/钉钉/ERP 轨迹数据集，全球零竞争。
4. **可回滚架构**：FeatureRegistry + flag 装配，每功能独立 commit 可回滚，迭代快而稳（V2 设计原则）。

## 三、市场与竞争分析

> 详细对比见 `/root/work/ai-wechat-cs-open-source-comparison.md`（2026-08-13）。以下为结论摘编。

### 3.1 方案全景与生态位

```
             合规性(封号风险)
                 ▲
      官方 iLink  │   RichCat(视觉) ◄── 我们的生态位
      (1v1,不能群聊)│        │
        CowAgent   │        │
                 ─┼─────────────────►  群聊/多账号能力
        WeChatFerry(wcf)     │
        (已停更,绑死3.9.x)    │
                 ▼ 企微官方API(门槛高) / Dify/MaxKB(企微侧)
```

| 方案 | 优点 | 致命短板 | 结论 |
|---|---|---|---|
| **腾讯官方 iLink 协议** | 合规零封号 | 仅 1v1、不能群聊、不能主动发起、24h 会话限制 | **1v1 场景首选通道，可作 RichCat 的加速通道** |
| **CowAgent + iLink** | AI 大脑 + 官方通道 | 同样受 iLink 限制，无群聊/无视觉兜底 | 同类竞品，但无视觉+群聊能力 |
| **WeChatFerry(wcf)** | 功能强 | 已停更、DLL 注入、实测失效 + 封号 | ❌ 已出局 |
| **wechaty / itchat** | 生态成熟 | 协议非官方、封号风险、个人号受限 | 仅合规场景之外使用 |
| **企微官方 API / Dify / MaxKB** | 企业级、合规 | 面向企业微信，个人微商/个人号无法用 | 企业场景竞品，非正面冲突 |
| **UI-TARS / 纯视觉框架** | 通用桌面 Agent | 无客服领域闭环（无 CRM/知识库/日报） | 竞品但缺行业深度 |
| **RichCat（视觉全流程）** | 个人号+群聊+合规+客服闭环 | 速度与规模上限低于协议方案 | **差异化最优位置** |

### 3.2 竞争壁垒与打法

- **短期（1-3 个月）**：先发者优势 + 开源口碑。RichCat 已开源自证，借比赛+社区把"工作记忆"概念占住。
- **中期（4-9 个月）**：垂直场景数据飞轮。达人建联场景沉淀的轨迹 + 策略卡语料，别人抄不走。
- **长期（10-12 个月）**：标准 + 组织记忆服务。发布开放 work-trace 规范（兼容 OTel GenAI spans），先发者定标准；组织记忆服务成为企业续费理由。

## 五、产品路线图（12 个月）

### Phase A — 根基（2026-08 ~ 11）

**目标**：把 Learn 从"叙事"变成"闭环" + 补工程化短板。

#### A1 v1.1.1（1 周内）—— 稳定性补丁
- 修复 QA 报告 D1–D4（脚本字段、文档回滚顺序、F9/F10 合并回滚说明、ts-node target）。
- 数据迁移兜底：旧 `worktrace/` 缺字段时默认值回归测试。

#### A2 Learn v1（4-8 周，v1.2.0 目标）
- 轨迹存储工程化：better-sqlite3 索引、保留策略、敏感信息脱敏开关。
- **真·人工接管录制**：引擎暂停 → 全局键鼠监听 + 截图 → `actor: 'human'` 示范轨迹。
- 经验卡片闭环：按 appType/联系人/场景检索 top-k 注入 prompt；trace 记录引用 → 卡片成功率统计。
- **Eval harness 产品化**：`npm run eval` 录制场景 × 模型 × prompt × 卡片开关矩阵评测，输出对比报告——"换模型效果可量化对比"。
- 回放升级：模型级回放（离线重跑 provider 对比新旧决策）。

#### A3 工程化（贯穿 Phase A）
- 单测补齐：`flags / emotion / vip / role-routing / injection / assembler` 纯函数单测（≥80% 覆盖核心层）。
- CI：GitHub Actions（PR 触发 typecheck + lint + build + 冒烟脚本）。
- 打包自动化：electron-builder 产物 + `latest.yml` 自动上传 Release（Win/macOS 双通道）。
- 冒烟回归：现有 3 个 smoke 脚本纳入 CI。

**Phase A 验收**：v1.1.1 发布；v1.2.0（Learn v1）发布；核心层单测 ≥80%；CI 绿。

---

### Phase B — 落地（2026-11 ~ 2027-05）

**目标**：补上任务层，跑通第一个垂直付费场景（达人建联），形成商业化雏形。

#### B1 任务层 v0（v2.0 核心）
> 依据 [Learn 规划 §七](learn-work-memory-plan.md)。这是比 Learn 更大的产品缺口：引擎从"被动循环"升级为"主动运营"。

| 能力 | 说明 |
|---|---|
| Campaign/建联名单 | 从 Wavith 等导入达人名单（CSV/API），批量建任务 |
| 按联系人状态机 | 待触达 → 已触达 → 已回复 → 洽谈中 → 成单/流失 |
| 主动发起会话原语 | 搜索联系人/添加好友/发起新会话（新 RPA 动作） |
| 跨天跟进调度 | N 天未回复 → 按策略卡选跟进话术；长生命周期任务 |
| 结果信号标注 | 自动（回复/通过好友）+ 手动（成单）→ 反哺卡片 stats 与回复率报表 |

#### B2 学习模式 v1（与 B1 并行）
- 录屏导入版：已有培训/优秀实操录屏 → 抽帧 → 视觉理解 → 拆出策略卡/SOP/红线清单 → 人工审核入库。
- 这是 L3"继承"的输入端，与人工接管录制互补，冷启动利器。

#### B3 达人建联垂直场景跑通
- 业务闭环：Wavith 公域找达人 → 名单导入 → 私域触达 → 多轮跟进（用策略卡）→ 结果回写 → 成功对话反哺知识库。
- **交付形态**：RichCat 内置"达人建联"工作台（或独立 Pro 版本），按运营席位订阅。

#### B4 双通道探索（iLink 加速）
- 1v1 场景：优先官方 iLink（合规、快），视觉作为群聊/复杂场景兜底；提供"通道优先级"配置。
- 评估成本：iLink 认证流程、消息速率、与任务层的集成。

**Phase B 验收**：任务层 v2.0 发布；达人建联场景跑通至少 1 个真实客户/自营案例（触达率/回复率/建联成功率可量化）；首笔付费或首批付费种子用户；iLink 通道 POC 结论。

---

### Phase C — 破圈（2027-05 ~ 08）

**目标**：从产品走向标准与生态，建立企业级护城河。

#### C1 开放标准
- 独立仓库 `work-trace-spec` 发布 v0.1：轨迹 schema + 校验器 + OSWorld/ATIF 转换器；兼容 OTel GenAI semantic conventions，扩展 GUI 字段（屏幕状态/坐标/人机来源/接管事件）。
- 首个**中文企业软件工作轨迹语料 + benchmark**（微信/钉钉/ERP 场景），附排行榜。

#### C2 组织记忆服务（企业版）
- 企业内网自托管服务端：trace/SOP 团队经验库、跨席位继承、管理 Dashboard。
- 这是商业版护城河与续费理由；RichCat 客户端作为数据采集端，服务端私有化交付。

#### C3 生态与社区
- Skill/SOP Hub（在 Provider Hub 之外）；skill-server 暴露轨迹/记忆 API，供 OpenClaw 等外部 Agent 消费。
- 每月轨迹数据集发布 + 技术报告/论文（AWM 闭环 + 中文企业场景是可发表点）。

**Phase C 验收**：work-trace-spec v0.1 发布并获社区引用；组织记忆服务企业版 MVP 有 1-2 家试用客户；GitHub Star 达行业影响力里程碑（如 2k+）；累计数据集规模公开。

## 六、技术架构演进

```
Phase A                                   Phase B                                   Phase C
┌──────────────────────┐        ┌───────────────────────┐        ┌────────────────────────┐
│ 现有: Electron+VLM   │        │ + 任务层(TaskEngine)   │        │ + work-trace-spec 规范  │
│  Visual RPA 闭环      │ ────▶  │   名单/状态机/调度      │ ────▶  │   校验器/转换器/benchmark │
│  FeatureRegistry F1-F10│       │ + 学习模式(录屏→知识)  │        │ + 组织记忆服务(自托管)   │
│  Learn v0 trace       │        │ + iLink 双通道(1v1加速)│        │ + Skill/SOP Hub 生态     │
└──────────────────────┘        └───────────────────────┘        └────────────────────────┘
        核心层不变:                                               ↓
  GenericChannelSession 状态机 / PromptAssembler 14段 /        开源生态位: 标准+语料+闭环
  Provider 抽象 / Store 体系 / RPA 原语
```

### 6.1 关键架构决策

| 决策 | 方向 | 理由 |
|---|---|---|
| 任务层形态 | 独立 `core/task/`，复用 Provider/RPA/Store，不入侵现有会话循环 | 保持被动客服引擎稳定，主动运营作为平行子系统 |
| iLink 接入 | 作为新 `ProviderChannel`（通道适配器），视觉仍是默认 | 通道可配置，群聊/复杂场景回退视觉 |
| 学习模式 | 统一 trace schema，录屏只是多一个输入适配器 | 一套记忆体系，多种输入端 |
| 组织记忆服务 | 独立仓库 + 私有化交付，客户端走 API 上报（可脱敏） | 本地执行承诺不变，企业版才有服务端 |
| 数据存储 | Phase A 引入 better-sqlite3 做轨迹索引；业务数据仍 JSON | 轨迹量大数据小，JSON 足够且可读 |

### 6.2 需持续维护的技术原则（沿用 V2 设计）

- 每功能独立模块 + flag + 独立 commit 可回滚；关闭零影响。
- 单向依赖（features → core/prompt/stores，禁止 feature 互 import）。
- 公共扩展字段独立 commit，注释块隔离。
- `npm run typecheck` / `lint` / `build` 作为提交门槛。

## 七、工程化与质量

### 7.1 测试策略（目标 ≥80% 核心覆盖）

| 层 | 内容 | 工具 |
|---|---|---|
| 单元 | flags/emotion/vip/routing/knowledge-injection/prompt-assembler/parseSmartReply | vitest 或 node:test |
| 冒烟（已有） | c1-prompt-smoke / f4-routing-smoke / f9-f10-smoke / qa-* | ts-node |
| 集成 | store 读写/feature hooks 装配/Eval 脚本 | vitest |
| E2E（可选） | Electron 拉起 + mock 设备跑完整会话 | Playwright(web) |

### 7.2 CI/CD（Phase A 落地）

- GitHub Actions：PR → typecheck + lint + 单测 + 冒烟；tag push → build + 上传 Release（win/mac）。
- `dist/` 保留历史安装包（v1.0.0 已示范，延续）。

### 7.3 发布节奏

- 修订版（x.y.z+1）：Bug 修复，按需。
- 次版本：Phase A/B 里程碑（v1.1.1 → v1.2.0 → v2.0.0）。
- 每次发布遵循 `docs/versioning.md`：CHANGELOG + tag + release notes + dist 保留。

### 7.4 代码质量纪律

- 代码审查：每次 PR 由 `code-reviewer` 过一遍（关键/高危必须修）。
- 提交纪律：conventional commits；每功能独立 commit。
- 架构审查：涉及 session-types/ai-client/main 装配的大改，先过 v2-design 原则再动手。

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| **微信平台封号/风控** | 🔴 高 | 视觉方案不注入 DLL，风险天然低于 wcf；但操作频率仍需拟人化（随机间隔/节流）；主动触达（Phase B）**必须**内置节流/每日上限；保留"人工确认"开关（F3 已有先例） |
| **iLink 接入依赖** | 🟠 中 | 作为加速通道而非唯一通道；视觉兜底始终可用；认证门槛评估后决定 |
| **数据合规（PIPL/个保法）** | 🟠 中 | 数据本地优先（已承诺"不上传服务器"）；组织记忆服务必须支持脱敏 + 企业内网自托管；客户联系方式等个人信息处理需告知与最小化 |
| **开源协议合规** | 🟢 低 | 基于 SightFlow（Apache 2.0），已保留 NOTICE/致谢；自身开源 Apache 2.0，注意商用版不混入闭源代码 |
| **视觉识别不稳定** | 🟠 中 | 布局测量（框选/VLM 双模式）已存在；关键流程留人工确认兜底；Eval harness 量化回归 |
| **单人开发带宽** | 🟡 中 | 里程碑严格取舍；复用现有 smoke/文档；比赛团队（4人）临时支援；商业化节点考虑外部支持 |

## 九、商业化路径

```
  ┌─────────────┐    ┌──────────────────┐    ┌──────────────────────┐
  │ 开源社区版   │──▶│ 达人建联工作台     │──▶│ 组织记忆服务(企业版)   │
  │ Apache 2.0  │    │ 垂直场景订阅       │    │ 私有化/SaaS          │
  │ 引流+口碑    │    │ 首个付费闭环        │    │ 护城河+续费           │
  └─────────────┘    └──────────────────┘    └──────────────────────┘
     免费              订阅制(¥/席位/月)        项目制/年费(私有化)
```

| 阶段 | 形态 | 定价参考 | 验证指标 |
|---|---|---|---|
| Phase B | 达人建联工作台（内置 RichCat 或 Pro 版） | ¥199–499/席位/月，或按建联量 | 付费用户数、月 ARR、建联成功率 |
| Phase C | 组织记忆服务（团队经验库/管理后台） | 私有化项目制（¥5w–30w）或 SaaS 年费 | 试用客户数、续费率、部署周期 |
| 长期 | 数据集/benchmark 商业化 + 咨询/培训 | — | 社区影响 → 商机转化 |

> 关键前提：付费能力必须长在**业务结果**上（建联成功率、回复率提升），而非"自动回复工具"本身——工具容易被免费替代，业务闭环不会。
