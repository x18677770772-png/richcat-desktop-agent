## 0. 执行摘要（先给结论）

**一句话：RichCat 的合规风险不是"能不能做"，而是"合同与设计上有没有把责任切干净"。**

RichCat 是**纯视觉桌面工具**（截图→识别→自动操作），不依赖任何微信协议/接口，因此：
- 不触碰《网络安全法》《刑法》关于**破坏计算机信息系统/非法获取计算机信息系统数据**的红线（区别于外挂/协议注入方案）；
- 不存储客户数据到第三方云（私有化部署），数据天然本地化；
- 但**处理聊天记录与客户个人信息这一行为本身**受 PIPL/数安/网安三重约束，必须通过"责任分层 + 文档化 + 技术控制"闭环。

**三层责任分层（贯穿全文的骨架）：**

| 主体 | 法律角色 | 核心义务 |
|---|---|---|
| **企业客户（买 RichCat 的 to B 客户）** | 个人信息处理者（受托委托人） | 取得终端客户授权、告知 AI 处理、响应删除/撤回、做安全评估 |
| **RichCat 财听猫** | 受托处理者/技术服务提供者（工具提供方） | 签 DPA、技术控制（隔离/加密/脱敏/审计）、不擅自处理/留存/对外提供客户数据 |
| **底层大模型（通义/DeepSeek/豆包/文心 等）** | 生成式 AI 服务提供者 | 履行算法备案/大模型备案、内容安全、输入信息保护；RichCat 用"合规模型白名单"约束 |

**三大关键判断：**
1. **RichCat 不面向公众提供生成式 AI 服务**（to B 工具，非 ChatGPT 式公众服务），因此《生成式AI服务管理暂行办法》的"提供者备案"义务主要落在底层大模型厂商，RichCat 需做的是**用已备案合规模型 + 内容安全 + 标识能力**，而非自己去备案大模型。
2. **RichCat 不生产深度合成内容**（不生成图像/音视频 deepfake，生成的是文本回复），《深度合成规定》的备案一般不触发；但仍需评估"舆论属性/社会动员能力"判定。
3. **合规是成交前提，不是成本**：安全问卷、法务一票否决、POC 前提——见第 5 章卖点，合规直接决定客单价（企业版 ¥5-30万 vs 订阅 ¥299）。

## 1. PIPL / 数据安全法 / 网络安全法：对聊天记录与客户个人信息的要求

### 1.1 三条法律的适用边界

| 法律 | 生效 | 适用点（对 RichCat 场景） |
|---|---|---|
| **《网络安全法》** | 2017-06-01 | 网络运营者安全保护义务；网络产品/服务安全；**不得利用网络从事损害他人合法权益**；个人信息收集的**最小必要 + 明示**原则；等级保护义务 |
| **《数据安全法》** | 2021-09-01 | **数据分类分级**（聊天记录属于企业经营数据，含客户个人信息）；安全保护责任（防止泄露/篡改/丢失）；重要数据保护与**风险评估与申报**；**政务/公共服务数据**特殊性 |
| **《个人信息保护法》(PIPL)** | 2021-11-01 | 处理个人信息的**告知同意**、目的限制、最小化、敏感个人信息单独同意、个人信息影响评估、跨境传输三重机制、受托处理者义务、删除权/撤回权 |

> 另有配套：《民法典》人格权编隐私权（聊天内容属通信秘密/隐私范畴）、《消费者权益保护法》第 29 条、GB/T 35273《信息安全技术 个人信息安全规范》、工信部《电信和互联网用户个人信息保护规定》与《APP违法违规收集使用个人信息行为认定方法》。

### 1.2 聊天记录与客户信息里到底有哪些"个人信息"（分类分级）

| 类别 | 示例 | 是否敏感个人信息（PIPL 第 28 条） | 处理要求 |
|---|---|---|---|
| 身份标识 | 昵称、微信号、姓名 | 一般个人信息 | 告知 + 同意 |
| 联系方式 | 手机号、地址、邮箱 | 一般（手机号在部分口径下被高度管控） | 告知 + 同意，最小化收集 |
| 业务数据 | 购买记录、订单号、偏好、售后诉求 | 一般 | 目的相关、最小化 |
| 画像/标签 | CRM 打标、VIP 分级、性格标签 | 一般（自动化决策需透明） | 须有明确目的与告知 |
| 财务账户 | 银行卡号、支付账号、余额截图 | **敏感**（PIPL 28 明确列示） | **单独同意** + 单独存储保护 |
| 健康医疗 | 体检/医疗/用药咨询（医美、口腔、门诊客户） | **敏感** | **单独同意** + 更强保护 |
| 行踪轨迹 | 定位、到店预约记录 | **敏感** | **单独同意** |
| 未成年人 | 不满 14 周岁客户（教育/亲子类行业） | **敏感**（PIPL 28） | **单独同意**（须取得其父母/监护人） |
| 生物特征 | 人脸截图、声纹（VLM 识别过程中可能短暂经过屏幕画面） | **敏感** | 尽量不采集；确需则单独同意 |

> **工程含义**：VLM 截图过程中，画面里可能偶然出现人脸/证件/卡号。合规设计上要**默认不存储原始截图到日志**（除非审计必需且加密），并对 OCR 文本**即时脱敏**。

### 1.3 合规链条：RichCat 场景的"合法处理链条"（必须闭环）

```
企业客户（处理者）────── 终端客户（信息主体）
     │ ① 取得终端客户授权（隐私政策/入群须知/客服话术中的 AI 处理告知）
     │ ② 与 RichCat 签《数据处理协议》DPA（委托处理）
     │ ③ RichCat 用已备案合规大模型（受托再委托，须经处理者同意）
     ▼
RichCat 工具（受托处理者）── 技术控制：隔离/加密/脱敏/审计
```

**每一环的法律要求（PIPL）：**

1. **处理者须有合法基础（第 13 条）**：聊天场景通常靠**"同意"**（入群时告知"本群由 AI 客服辅助接待"）；其他可选基础（合同履行、已公开信息合理范围）不适合聊天数据，**别裸奔用"合法利益"搪塞**。
2. **告知义务（第 17 条）**：告知处理者名称、目的、方式、种类、保存期限、行使权利的途径。企业客户必须**在添加好友/入群/首次对话时**向终端客户告知"AI 参与接待"。
3. **敏感个人信息单独同意（第 29 条）**：一旦聊天涉财务/医疗/未成年人/行踪，须**单独弹出确认**（不能混在总隐私政策里）。RichCat 应提供**"敏感信息检测 → 阻断采集或单独确认"的开关**。
4. **最小必要（第 6 条，网安法 41 条）**：只处理完成接待所需的信息；不做与客服无关的采集。
5. **保存期限最小化（第 19 条）**：聊天记录保留期限由处理者决定并向信息主体告知（如"保留 12 个月"），到期删除或匿名化。RichCat 提供**保留期策略 + 到期自动清理**。
6. **受托处理者义务（第 21 条）**：RichCat 必须：
   - 按照约定处理，**不得超出约定目的**；
   - 对处理情况进行记录（审计）；
   - **不得转委托给第三方**（除非取得处理者同意，且对再受托方承担同等义务——对应"合规模型白名单"）；
   - 处理完成后**删除或返还数据**（合同终止条款）；
   - 未经处理者同意，**不得访问/留存/对外提供**其数据。
7. **删除权/撤回权（第 15/47 条）**：RichCat 需支持终端客户删除其个人信息——落地为"企业客户在后台一键导出/删除某客户档案"，RichCat 提供接口与证明。
8. **个人信息保护影响评估 PIA（第 55 条）**：使用 AI 处理个人信息属于**高风险处理**，处理者应开展 PIA 并留存记录。RichCat 提供**PIA 模板 + 支持材料**，帮助企业客户快速交差。
9. **自动化决策（第 24 条）**：AI 自动回复、客户分级、标签属于自动化决策——处理者须保证**透明**（可解释"为什么这样回/为什么打这个标签"），RichCat 的工作记忆引擎恰好提供"决策过程留痕"，是合规加分而非负担。

### 1.4 企业客户自用聊天数据 = 第三方个人信息，风险归属要写进合同

RichCat 处理的是**企业客户自己的客户**（终端客户）的个人信息。这带来一个重要结论：

> **RichCat 无义务、也无权对"终端客户是否同意"做最终审查——但必须在 DPA 中让企业客户作出"已取得合法授权"的陈述与保证，并约定因授权缺失引发的纠纷由企业客户承担。**

（反向看，这也是卖点：RichCat 把授权责任模板化交付给企业客户，帮它落地，而不是替它承担。）

## 2. AI 监管：生成式AI办法 / 深度合成 / 算法备案——适用性判断与应对

### 2.1 三部法规的适用性判定表

| 法规 | RichCat 是否属于监管对象？ | 判定理由 | 应对策略 |
|---|---|---|---|
| **《生成式AI服务管理暂行办法》**（2023-08-15） | 工具层面**非直接监管对象**；但受其约束的合规义务需传导 | 该办法规制"面向境内公众提供生成式AI服务"的**提供者**。RichCat 向企业提供 to B 工具，非直接面向公众的生成式服务；**底层大模型厂商才是提供者** | ①只对接**已履行备案手续的合规大模型**（大模型备案/上架清单，见 2.2）；②产品内置**内容安全**（敏感词过滤/拒答/人工接管）；③提供 **AI 生成内容标识**能力（回复水印/页脚说明"由 AI 辅助生成"）；④不把用户输入用于训练（默认零样本留存/可关闭），符合办法第 9 条"不得非法留存可识别身份信息" |
| **《深度合成管理规定》**（2023-01-10） | **一般不适用的可能性高** | 深度合成指"利用深度学习等合成**图像、音频、视频**"等。RichCat 生成的是**文本客服回复**，非深度合成内容 | 留法律备忘录记录判定结论；若未来扩展"AI 语音外呼/数字人"功能，**需重新评估**备案 |
| **算法备案（《互联网信息服务算法推荐管理规定》2022-03-01 / 生成式AI办法 17 条）** | **RichCat 本身大概率无需备案**；底层大模型需备案 | 备案门槛是"**具有舆论属性或社会动员能力**"。企业客服回复不属于舆论属性；RichCat 无独立面向公众的信息分发属性。但**底层生成式大模型属典型备案对象** | ①自查留档《算法/深度合成备案适用性法律备忘录》；②向客户提供**合规模型清单**（已备案模型列表），把"是否备案"交给已备案厂商背书；③合同约定大模型厂商的备案与内容安全义务传导 |

### 2.2 合规模型白名单（RichCat 的内置安全闸门）

RichCat 通过 Provider 机制支持多种大模型。企业版应对**模型准入**做清单化约束：

| 维度 | 要求 | 落地 |
|---|---|---|
| 已备案 | 使用网信办已备案/已上线的大模型（通义千问、DeepSeek、豆包、文心一言、腾讯混元、Kimi 等均已完成备案） | 白名单 + 默认推荐国产已备案模型 |
| 数据属地 | 境内模型=数据不出境（最优）；境外模型（OpenAI/Claude 等）=触发跨境合规（见 3.5） | 默认境内；境外需单独配置并给客户出境合规指引 |
| 零留存 | 模型侧不把企业输入用于训练/留存 | 合同 + 服务商承诺 + 产品设置"数据不回传训练" |
| 内容安全 | 模型自带安全对齐 + RichCat 层兜底 | 敏感词库 + 拒答/人工接管 + 审计留痕 |

### 2.3 AI 内容标识（生成式AI办法 12 条 / 深度合成规定 17 条）

- 面向公众生成内容，法律要求"**添加不影响使用的标识**"。企业客服回复发给终端客户，按审慎口径应具备标识能力。
- RichCat 产品建议：**可配置**"AI 辅助回复"尾注/首行水印（如"本条由 AI 辅助生成，人工可接管"），按行业与客户偏好开关（医美/金融/医疗建议默认开启，透明反而获信任）。

### 2.4 内容安全与投诉机制（生成式AI办法 第 10/15 条）

- 建立**内容安全策略**：涉政、涉恐、涉黄、违法广告、虚假宣传的输入/输出拦截；情绪风险（F5）与敏感话题优先转人工。
- 建立**投诉举报渠道**：RichCat 官网 + 后台提供投诉入口；处理时限承诺。
- 企业客户侧：把"AI 回复不当"纳入其客服投诉流程，RichCat 提供证据导出支持溯源。

## 3. 企业私有化部署的合规设计（数据隔离 / 脱敏 / 审计 / 跨境 / 等保）

> 设计目标：**让企业客户能用一句话向自己法务交代——"数据在我的环境里，我有日志、能脱敏、能删、能导出、不出境。"**

### 3.1 部署形态与数据边界

| 形态 | 数据驻留 | 适用 |
|---|---|---|
| **纯本地/内网部署（企业版首选）** | 值守机 + 管理后台全部在客户内网；数据不出客户环境（除大模型推理的文本请求） | 私域电商、医美、金融、政务类客户 |
| **本地软件 + 境内合规大模型 API** | 数据文件本地，仅脱敏后文本发送至境内模型 | 默认推荐形态 |
| 本地软件 + 境外模型 | 触发跨境合规（3.5），默认不推荐 | 出海/有跨境需求的客户 |

**数据边界铁律**：RichCat 官网/云侧**只承载授权、License、升级与告警元数据**（不含聊天内容），**不汇聚企业客户的聊天数据**——这是"RichCat 不是个人信息处理者"这一主张的事实基础，必须写进隐私政策与宣传口径。

### 3.2 数据隔离（多租户/多账号）

- **物理隔离**：每企业独立部署（交付服务器/虚拟机独立）；私有化大客户数据文件、数据库、密钥、日志目录相互隔离。
- **逻辑隔离（同一交付服务器托管多客户时）**：独立数据库/独立 schema + 租户 ID 全链路过滤 + 访问密钥隔离；**禁止跨租户查询**。
- **账号级隔离**：值守机每客服账号独立数据目录（沿用 `--profile` 的隔离基因），工作记忆/客户档案按账号归属。
- **隔离验证**：交付时提供"租户隔离自测"用例（A 租户管理员无法看到 B 租户任何数据），写入验收清单。

### 3.3 脱敏（Privacy by Design）

| 数据形态 | 脱敏规则 | 落地 |
|---|---|---|
| 日志 | 手机号/身份证/银行卡/地址/邮箱**自动打码**后再写日志与日报 | 正则 + 模型二次识别双保险；脱敏后日志才能进看板/审计导出 |
| 日报（F6） | 客户名、联系方式脱敏，只保留行为统计 | 模板内置脱敏字段 |
| 审计导出 | 支持"脱敏导出"与"明文导出（需高权限）"两档 | RBAC 控制 |
| 截图原始文件 | **默认不落盘**；确需留痕则加密存储 + 限期清理 | 设置项 + 默认关 |

### 3.4 审计与留痕（G4 落地，append-only）

- **全链路审计**：谁/何时/对哪个客户/做了什么操作；AI 每条回复原文、人工接管与被接管原因、配置变更、登录会话、导出行为，全部 append-only 落审计库。
- **防篡改**：哈希链（前条哈希 + 时间戳 + 随机数）、只读存储、审计管理员账号双人复核。
- **可查询可导出**：≤60s 导出 PDF/CSV，带水印与导出人留痕。
- **法定用途**：满足 PIPL 第 21 条受托处理记录义务、企业内控、纠纷举证、监管检查。

### 3.5 跨境数据传输（PIPL 第 38 条）

- **默认零跨境**：境内部署 + 境内已备案模型 = 数据不出境，**不触发**出境安全评估/标准合同/认证。
- **若客户确需境外模型**：RichCat 提供指引——①取得终端客户**单独同意**；②通过**标准合同/安全评估/认证**三选一；③要求境外模型商签署数据处理条款；④出境前脱敏（能去标识化的尽量去标识化）。
- **销售话术**：境外方案 RichCat 只做技术支持方，**合规责任在客户**（合同明示）。

### 3.6 安全基线（G8）与等级保护

| 控制项 | 要求 |
|---|---|
| 访问控制 | 管理后台登录认证 + RBAC（管理员/坐席/只读）+ 可对接企业 SSO/OAuth + 离职回收 |
| 加密 | 存储加密（SQLite SQLCipher 级）+ API Key 密钥托管加密 + 传输 TLS |
| 密钥管理 | 密钥与数据分离、可轮换、托管在客户侧 |
| 等级保护（等保） | 轻量部署支持客户做**等保二级**自查材料；政务/金融类大单支持**等保三级**材料配合（等保是客户自己申报，RichCat 提供技术自评表与清单） |
| 数据备份与销毁 | 定期备份、备份加密；合同终止**删除或返还**数据并提供删除证明（PIPL 21 条受托义务） |
| 漏洞与更新 | 安全更新通道、漏洞响应承诺（如 48h 响应） |
