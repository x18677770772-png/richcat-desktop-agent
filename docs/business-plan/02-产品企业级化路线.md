# 02 · 产品企业级化路线：从 v1.1.0 个人版到"最小可售企业版（MSE）"

**Status**: Draft — In Review
**Author**: Alex（产品经理）  **Last Updated**: 2026-08-20  **Version**: 0.9
**Stakeholders**: 技术负责人、商业化负责人、市场/销售、客服（内部）
**目标**：定义 90 天商业化（100 万 RMB 营收）所需的产品企业级化最小路径，明确「做什么、按什么顺序做、做到什么程度才算可卖」。

---

## 0. 战略判断：为什么是"系统"而不是"工具"

v1.1.0 已经验证了单机价值：AI 自动回复、CRM 建档与长期记忆、知识库、5 种人设、图片识别、F1–F10 功能体系、工作记忆引擎。这是一个**跑得通的个人版**。

但个人版本质是"一台机器 + 一个操作者 + 一个账号"。企业买单的对象不是"帮我自动回复的工具"，而是"**7×24 不下班、不离职、越用越懂我的客服团队**"。这意味着产品形态必须从：

> 单机桌面应用（谁在电脑前谁用）→ 企业级系统（多账号值守 + 统一管理 + 留痕合规 + 可度量可承诺）

**一句话：90 天里我们不追求把功能堆满，我们追求把"企业愿意付钱、我们能交付、客户不敢换掉"的最小闭环做扎实。** 卖的是"无人值守的客服运营体系"，不是"又一个桌面软件"。

---

## 1. 现状盘点：v1.1.0 已有能力 → 企业级差距

| 维度 | v1.1.0 现状 | 企业级要求 | 差距级别 |
|---|---|---|---|
| 自动回复/画像/知识库/人设 | 已具备（含 F9 分级知识库、F10 提示词体系） | 需集中配置、按账号下发、可回滚 | 中（配置面，非重建） |
| 多账号 | `--profile` 手动多开，数据完全隔离，无统一视图 | 控制台统一管理、账号级配置继承、跨账号看板 | **高（形态重构）** |
| 人工接管 | F2 识别并通知，事件有记录 | 接管分配、值班表、接管流程留痕、管理者介入 | 中高 |
| 情绪/风险 | F5 检测+打标+提醒（本地） | 实时告警推送（企微/钉钉/飞书机器人）、风险升级流 | 中 |
| 服务数据 | F6 每日 Markdown 日报（单机） | 集中看板、满意度/转化指标、月度报告、SLA 报告 | **高** |
| 团队协作 | 无（单用户） | 多管理员、RBAC、接管分配、知识库审核上线 | **高（缺失）** |
| 数据 | 本地 SQLite 明文存储，API Key 明文 | 加密、脱敏、权限边界、审计、合规 | **高（合规刚需）** |
| 对外接口 | 无 | 开放 API、Webhook、与 CRM/工单/BI 集成 | 高（缺失） |
| 授权 | Apache 2.0 开源 | 企业版闭源 + License 按坐席授权、试用激活 | **高（商业前提）** |
| 部署 | 单机桌面，依赖有人值守 | 值守机 Agent 化、远程监控、异常自愈、SLA | **高（交付前提）** |

**结论**：90 天内**不需要重做 AI 内核**——核心竞争力（工作记忆、视觉 RPA、F 体系）已经站在及格线以上。真正的缺口集中在**管理面、合规面、交付面、商业面**四层外壳。

## 2. 企业级部署关键缺口（九大项）

每项标注：现状 → 缺口 → 对销售/交付的影响 → 优先级（P0=不解决不能签单；P1=显著影响成交与交付效率；P2=影响续约与规模化）。

### G1 私有化与部署形态（P0）
- 现状：仅单机桌面，`--profile` 多开，依赖操作者在本机操作激活窗口。
- 缺口：企业要求可控的部署方式——内网/客户服务器可部署的管理后台；每客服账号一台"值守机"（低配 Windows 或 Windows 虚拟机），Agent 常驻、开机自启、崩溃自愈。
- 影响：没有可部署形态=无法交付。这是"能不能卖出去"的第一道门。
- 落点：值守机 Agent（继承 v1.1.0 内核）+ 可本地部署的轻量 Web 管理后台。

### G2 多账号 / 多租户治理（P0）
- 现状：`--profile` 是"数据隔离"，不是"统一管理"。账号多了不可运维。
- 缺口：控制台侧统一管理 N 个客服账号（N=5–20 起步）：账号注册/启停、配置模板下发（人设/知识库/模型/路由/接管阈值按账号继承+覆盖）、账号级用量与健康状态。租户侧：企业 A 与 B 的数据严格隔离（即便共用同一台交付服务器），数据归属、备份、销毁有明确边界。
- 影响：没有多账号治理，销售只能卖"一个号"，客单价上不去；没有租户隔离，不敢承诺私有化。

### G3 管理后台（Admin Console）（P0）
- 现状：设置/客户/知识库均为单机窗口。
- 缺口：一个 Web 控制台完成——账号与权限（RBAC，管理员/坐席/只读）、集中配置下发、知识库与人设管理、值班表与接管规则、实时服务看板（服务量/接管/风险/满意度/转化线索）、策略中心（情绪阈值、接管阈值、话术版本）。
- 影响：管理后台是"系统"与"工具"的分界，是 demo 时决策者眼睛看的第一个东西。

### G4 审计日志与合规（P0）
- 现状：F2 接管有事件记录，但非完整审计链路。
- 缺口：全链路留痕——谁/何时/对哪客户/执行了什么操作；AI 每条回复原文、人工接管与被接管原因、配置变更、账号操作；可查询、可导出（PDF/CSV）、防篡改（append-only）；满足《个人信息保护法》《数据安全法》及客户内部风控审计要求；日志与日报自动脱敏（手机号/身份证/地址）。
- 影响：**审计是企业采购的第一道法务闸门**。没有审计，法务一票否决，销售谈不到报价。

### G5 团队协作与接管治理（P1）
- 现状：F2 接管通知到本机。
- 缺口：接管事件升级到团队——谁接管（值班表/按客户归属分配）、接管处理状态（已接手/已解决/超时）、管理者可介入、客户档案多人可见但按角色授权；知识库条目与人设话术"审核后上线"流程，防止一线随意改。
- 影响：企业要的是"AI 是人团队的一员"，不是"AI 代替人"。没有协作面，客户会认为只是个自动化脚本。

### G6 开放 API 与集成（P1）
- 现状：零对外接口。
- 缺口：REST API v1——客户档案同步（从企业已有 CRM 拉/推）、知识库批量同步、接管/风险/日报事件 Webhook（推送到钉钉/企微/飞书机器人或自建系统）、数据导出（对接 BI）。
- 影响：中大型客户 90% 有"必须对接我们现有系统"的要求；API 是谈成"第一个大客户"和防止被竞品替换的双重武器。

### G7 SLA 与值守可用性（P1）
- 现状：无心跳、无监控、宕机无人知——对客户是"客服电话断了没人管"。
- 缺口：值守机心跳上报（Agent 常驻 + 看门狗自动重启 + 崩溃自愈）；控制台全局健康页；异常（掉线/窗口异常/长时间未响应/模型超时）实时告警推送；月度可用性报告（SLA 依据）；支持在 SLA 条款里承诺"可用率 ≥ 99% 值班时段、故障 15 分钟内告警"。
- 影响：**无人值守是卖点也是雷**——客户敢把售后放给机器，前提是"坏了必须有人知道"。SLA 是从"软件采购"升级为"服务采购"的定价基础。

### G8 安全基线（P0）
- 现状：SQLite 明文、API Key 明文、无登录认证。
- 缺口：管理后台登录认证（可对接企业 SSO/OAuth）、账号会话与权限边界、员工离职回收；本地数据加密（SQLite 加密 + 密钥托管）、API Key 加密存储、传输 TLS；日志脱敏；可交付《安全白皮书》与《数据隐私承诺书》（PIPL 响应）；杀软白名单与安装包签名。
- 影响：**安全问卷是招投标/大客户的必答题**。过不了问卷，连 POC 机会都没有。

### G9 计量与授权商业外壳（P0）
- 现状：Apache 2.0 开源、无授权体系、无用量计量。
- 缺口：企业版闭源 + License 服务（按坐席/按账号授权、试用激活、离线授权、到期续费）；用量计量（会话量/消息量/模型 token 成本/接管次数）与配额控制；用量报表，为"基础年费 + 用量/坐席"的 SaaS 化计费铺路。
- 影响：没有 License=无法收费；没有计量=无法从"一次性卖断"走向"按服务订阅"（后者才是 100 万营收里可预测的部分）。

> **优先级小结**：P0 = G1 部署形态、G2 多账号/多租户、G3 管理后台、G4 审计合规、G8 安全、G9 授权计量 —— 这六项构成 MSE 的骨架，缺任何一项企业版都"不可售或不可交付"。P1 = G5 协作、G6 API、G7 SLA —— 决定成交速度与客单价。

## 4. 最小可售企业版（MSE）定义

### 4.1 一句话定义

> **MSE 是一套能支撑 3–20 个客服账号、5–10 名管理员/坐席、在 1–3 天内完成私有化部署并承诺 SLA 的"AI 客服运营系统"——它具备多账号值守、集中管理、审计合规、安全基线、授权计量与团队协作的最小完整闭环。**

### 4.2 产品形态

- **值守机 Agent（Windows）**：继承 v1.1.0 全部 AI 内核（自动回复/CRM/知识库/人设/F 体系/工作记忆），升级为单账号稳定值守、崩溃自愈、心跳上报的常驻服务。
- **管理后台 Web 控制台**：可部署在客户内网或我方交付服务器，承载多账号管理、配置下发、审计日志、健康告警、团队接管、价值看板。
- **License 服务**：按坐席/账号授权、试用/正式/续费三种状态。
- **告警通道**：钉钉/企微/飞书机器人推送（接管、风险、宕机）。

### 4.3 MSE 功能包（Must 全含 + Should 中 S2/S4 精简版）

| 模块 | 内容 | 说明 |
|---|---|---|
| 多账号值守 | Agent 化值守机、账号注册/启停/健康、配置模板下发 | M1/M2/M6 |
| 管理后台 | 账号与权限、配置中心、知识库/人设管理、值班表、实时看板 | M2/M8 |
| 审计合规 | 全链路留痕、查询/导出、脱敏、安全白皮书 | M3/M4 |
| 安全 | 登录认证 + RBAC、数据与 Key 加密、TLS、日志脱敏 | M4 |
| 授权计量 | License 按坐席、试用激活、会话/消息用量报表 | M5/M9 |
| 团队协作 | 接管队列、按值班/归属分配、状态跟踪、管理者介入 | M8 |
| 服务价值 | 响应时长/转人工率/满意度/转化线索基础看板 | S2（精简） |
| 告警 | 心跳监控、宕机/风险/接管实时推送 | M6/S6（精简） |
| 交付包 | 部署手册、初始化向导、培训、验收清单、话术模板 | M7 |

### 4.4 定价锚点（供商务参考，MSE 起步）

- **起步版**：5 坐席，¥3.8 万/年（试用 14 天）
- **标准版**：10 坐席，¥6.8 万/年（含 API v1 基础额度 + SLA）
- **专业版**：20 坐席，¥12.8 万/年（含 API 全量 + 专属部署 + 月度 SLA 报告）
- **扩展**：超出坐席按 ¥300/坐席/月；可选"会话量/消息量"计量包
- 90 天 100 万目标 ≈ 标准版 ×10–12 家 或 专业版 ×8 家 + 起步版若干 —— **这意味着 MSE 必须轻交付（签约到上线 ≤ 3 天、≤1 人日），销售节奏以"1 周 1 家"为目标。**

### 4.5 MSE 交付物清单

**产品/软件交付物**
1. 值守机 Agent 安装包（Windows x64，签名） + 初始化向导
2. 管理后台 Web 控制台（含 Docker 化部署包，支持内网）
3. License 服务端 + 激活器（离线授权支持）
4. 告警通道集成（钉钉/企微/飞书机器人）

**文档交付物**
5. 《企业版部署手册》（含值守机规格：建议 4C8G、Windows 10/Server、预留微信客户端常驻）
6. 《运维与故障处理手册》（看门狗/自愈/常见故障）
7. 《管理员操作手册》与《坐席值班手册》
8. 《安全白皮书》与《数据隐私承诺书》（PIPL 响应模板）
9. 《验收清单》（功能验收 + 合规验收 + SLA 验收）

**销售/商务交付物**
10. 一页纸方案（MSE 价值主张）
11. 可重复 demo 环境（含演示账号/话术/数据）
12. POC 方案模板（2 周，3–5 个账号）
13. 报价单模板与合同条款模板（含 SLA 条款、数据归属条款）
14. 竞品对比表（个人号×群聊×视觉×合规 vs. iLink 1v1 局限、WeChatFerry 停更）
15. 安全问卷应答模板（对接招投标/大客户法务）

### 4.6 MSE 验收标准（Gate）

- 可独立完成：从空机部署到 5 账号上线 ≤ 1 人日
- 连续 7×24 值守 0 人工干预、掉线自愈率 ≥ 95%、告警延迟 ≤ 15 分钟
- 全操作审计可回溯、导出 ≤ 60s、日志脱敏生效
- 授权校验拦截未授权实例；试用→正式→续费链路完整
- 通过内部安全自测清单 100%（登录/RBAC/加密/TLS/脱敏）
- 完成 2–3 家真实客户交付并形成标准交付 SOP

## 5. 与企业购买动机挂钩（五动机 × MSE 功能映射）

| 购买动机 | 客户内心问题 | MSE 怎么回应 | 对应功能 | 卖点语言 |
|---|---|---|---|---|
| **降人力成本** | "我能否少招/少让客服熬夜值班？" | 7×24 无人值守，接管只在机器搞不定时叫人；每账号替代约 0.5–1 人夜间/节假日值守 | M1/M6/M8、F2 接管 | "1 套系统顶 3 个夜班客服，接管率可量化到月报" |
| **提满意度** | "客户会不会被机器人气走？" | 快速响应（秒级）+ VIP 差异化 + 情绪/风险实时识别并升级人工；响应时长与转人工率进看板 | F3/F5/S2/S6 | "响应从分钟级到秒级，情绪风险秒级告警保护关系" |
| **复购** | "老客户会不会觉得没被记住？" | 长期记忆跨会话记住每位客户、待跟进提醒、知识库让回答贴合业务；复购线索进看板 | CRM/长期记忆/F7/S2 | "AI 记得每个客户的过去，复购时机一个不漏" |
| **客单价** | "AI 能帮我把客单价做上去吗？" | 销售顾问人设 + 多角色路由 + VIP 专享话术，销售转化数据进看板 | F4/F3/人设/S2 | "销售/售后/专家自动路由，VIP 用专属话术成交" |
| **转介绍** | "我怎么向同行证明这套系统好用？" | 服务日报 + 月度 SLA 报告 + 价值看板，让老板有可分享的服务数据；交付即生成推荐素材 | F6/N2/S2 | "每月一张服务战报，老板自己愿意发朋友圈" |

**核心逻辑**：MSE 的每个"售点"都必须能在交付后变成"可度量的事实"（接管率、响应时长、满意度、转化线索、可用率），而不是一句口号——这既是购买动机的兑现，也是续约和转介绍的引擎。

## 7. 风险与开放问题

| 风险/问题 | 影响 | 缓解 |
|---|---|---|
| 开源分叉风险：v1.1.0 为 Apache 2.0，竞争对手可基于社区版做企业服务 | 高 | 尽早完成企业版闭源分叉 + 品牌/许可策略；将工作记忆、多账号治理、审计留痕作为非开源差异面 |
| 值守机物理依赖：需真实微信客户端常驻 + 每账号一台机器 | 中高 | 明确值守机规格与客户环境前置条件；企微优先降低环境不确定 |
| 视觉操作偶发误判（极端 UI/弹窗/验证码） | 中 | 自愈 + 告警兜底；F2 接管阈值在交付时按客户业务校准 |
| LLM token 成本与计量透明度 | 中 | S3 用量计量进 MSE；商务上明确"年费含基础额度 + 超出另计" |
| 90 天多客户交付的人力瓶颈 | 高 | 交付包（M7）+ 远程交付 + 部署向导，把单客户交付压到 ≤1 人日 |
| 合规跨行业差异（医疗/金融等强监管） | 中 | MSE 先打合规要求适中的行业（电商/教育/本地生活）；强监管行业走 POC 加定制 |
