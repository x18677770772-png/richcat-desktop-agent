## 0. 一句话定义与设计原则

> **中央管理后台 = 我方托管的「控制面」（SaaS 为主，私有化可选）＋ 客户侧值守机 Agent 的遥测终端。它只碰元数据（License/心跳/用量统计/告警/升级），不碰客户聊天内容与个人信息。**

四条硬设计原则（贯穿全文）：

1. **元数据边界（合规铁律，来自 10 分卷 3.1）**：云侧只承载授权、心跳、用量统计、告警、升级元数据，**不汇聚聊天内容/客户个人信息**；所有遥测在 Agent 侧完成脱敏后上行。
2. **无人值守 = 信任开关（G7）**：掉线 15 分钟内必须告警；Agent 崩溃自愈率 ≥95%；可用率 ≥99%（值班时段）才有资格写进 SLA。
3. **可演进不可重写（CEO 定向）**：90 天内「轻管理后台 + 心跳告警」即可 demo 签单（不做重多租户云版）；但存储/消息/租户隔离按 500+ 可平滑扩的骨架设计，避免二次重构。
4. **沉淀学习只给聚合层（任务要求第 9 点）**：跨实例学习只消费「匿名统计/聚合」，不给原文；聚合以「群组」为粒度，k-匿名（≥10 实例才出数）。

**角色边界**：
- **值守机 Agent** 是遥测的「生产者」和指令的「执行者」：采集脱敏遥测、上报心跳、接收配置/升级指令并自检回滚。它是客户侧的唯一数据入口，也是「数据本地化」的物理边界。
- **控制面** 是「聚合者 + 治理者」：舰队视图、告警、License、配置下发、审计。**它不是聊天数据的接收方**——这条红线由「Agent 侧脱敏 + 上报 Schema 白名单」双重保证（见 §2.4 / §7.4）。

### 1.2 数据流图

**遥测上行流（Agent → 控制面）**

```
值守机 Agent
   │ ① 心跳/用量/错误事件（HTTPS + mTLS，JSON，脱敏后）
   ▼
Agent 网关（校验签名 → 租户路由 → 写入 Kafka）
   │ ② Kafka topic：telemetry.heartbeat / telemetry.usage / telemetry.error
   ▼
消费侧
   ├─ heartbeat 消费者 ──▶ TDengine（时序健康指标）──▶ 舰队视图 / 可用率报表
   ├─ usage 消费者 ──▶ PG 用量日桶（聚合）＋ 原始归档 OSS（90d）
   ├─ error 消费者 ──▶ ① 告警引擎规则评估 ② SSE 实时错误流推送浏览器
   ├─ alert 事件 ──▶ 告警中心 + DingTalk/WeCom/Feishu webhook
   └─ 每日聚合 job ──▶ 学习仓（匿名群组聚合，k-匿名阈值）──▶ AI 工程师只读 API
```

**配置/升级下行流（控制面 → Agent）**

```
管理员/运维
   │ ③ 编辑配置模板 / 发布新版本（审批 + 灰度策略）──▶ PG(config_revisions / releases)
   ▼
Agent 网关
   │ ④ 在心跳响应里捎带 pending commands：{config_update, upgrade, restart, alert_ack}
   ▼
值守机 Agent
   │ ⑤ 拉取配置/升级包（Ed25519 签名 + SHA256 校验）→ 应用 → 自检 → 失败自动回滚
   │ ⑥ 结果上报（apply_result）→ 控制面记录版本/配置生效状态 → 舰队视图更新
```

**关键交互模式**：控制面 → Agent 的「下行」**默认不主动建立长连接**，而是搭在心跳响应的捎带命令（long-poll）上——简单、穿透 NAT、防火墙友好。仅「紧急重启」等可选项提供 WebSocket 即时通道。这是经典的 IoT 设备管控模式（类 MDM），也是离线升级策略（§8.4）的基础。

## 2. 遥测协议与数据模型

### 2.1 传输协议

- **传输**：HTTPS/TLS 1.3 + **双向 mTLS**（Agent 客户端证书，装机时签发）+ 站点 Token（租户级）。
- **上报周期**：
  - 心跳：1 次/60s（业务时段可加密为 30s，看门狗触发时立即上报）。
  - 用量：本地聚合后每 10 分钟批量上报一次（桶内 6 个子桶，崩溃最多丢 10 分钟统计）。
  - 错误：**实时上报**（发生即发，控制面告警 ≤15min 的 SLA 依据）。
  - 告警：Agent 本地即时告警（如微信掉线）也走 error/alert 事件实时上行。
- **下行**：心跳响应捎带命令队列（JSON）；`config_update` / `upgrade` / `restart` / `ack`。
- **离线缓冲**：Agent 本地持久化队列（上限如 5 万条 / 200MB，先进先出，满了丢最旧），断网重连后按原时间戳重放；重放数据打 `replayed:true` 标记，避免重复统计。

### 2.2 统一 Telemetry Event Schema（JSON）

所有事件共用信封，`event_type` 区分四大类：

```json
{
  "schema_version": "1.0",
  "event_id": "7f3c9a2e-...",                    // UUID，幂等去重
  "event_type": "heartbeat|usage|error|alert",    // 四大类
  "occurred_at": "2026-08-20T10:00:00.000Z",
  "producer": {
    "tenant_id": "tn_8f2k...",                    // 租户 ID（全链路）
    "site_id": "site_9x1...",                     // 站点/部署单元
    "agent_id": "ag_5ab...",                      // 值守机实例
    "profile_id": "p_d3e...",                     // 客服账号（脱敏映射，非真实账号）
    "machine_id": "hmac_sha256_of_hw_fingerprint",// 机器指纹哈希
    "agent_version": "1.1.0",
    "runtime": {"vlm": "qwen-vl-3.5", "llm": "deepseek-v3", "os": "win10-22h2"}
  },
  "tags": {"region": "cn-east", "channel": "stable"},
  "payload": { ... }                              // 按 event_type 各自定义（见下）
}
```

### 2.3 四类事件 Payload

**① heartbeat（保活 + 版本 + 状态 + 瞬时健康）**

```json
{
  "event_type": "heartbeat",
  "payload": {
    "state": "online",                            // online | degraded | starting
    "uptime_s": 86400,
    "watchdog": {"status": "ok", "restart_count": 2, "last_restart_at": "..."},
    "wechat_client": {"state": "logged_in"},      // logged_in|logged_out|captcha|window_missing
    "active_sessions": 3,
    "messages_today": 152,                        // 本地瞬时计数，不含内容
    "resources": {"cpu_pct": 23, "mem_pct": 41, "disk_free_gb": 85},
    "queue_backlog": 0                            // 本地待上传统计缓冲
  }
}
```

**② usage（用量事件：只统计，不涉内容）**

```json
{
  "event_type": "usage",
  "payload": {
    "bucket_start": "2026-08-20T10:00:00Z",      // 聚合窗口 10min
    "session_count": 12,
    "message_count": 86,
    "auto_reply_count": 74,
    "human_handover_count": 3,
    "visual_rpa_count": 5,
    "llm_calls": 90,
    "llm_input_tokens": 120000,
    "llm_output_tokens": 45000,
    "llm_cost_cents": 86,                         // 成本（分）——计量计费依据
    "model_error_count": 1,
    "timeout_count": 1,
    "avg_response_s": 1.8,
    "p95_response_s": 3.2
  }
}
```

**③ error（错误事件：结构化，去标识化）**

```json
{
  "event_type": "error",
  "payload": {
    "severity": "fatal|error|warning",
    "error_code": "WECHAT_SESSION_LOST",          // 枚举码（见下）
    "category": "crash|alert|visual|model|network",
    "component": "vlm|llm|wechat|watchdog|rpa",
    "stack_hash": "sha256_of_normalized_stack",   // 不上报原文栈，只上报哈希
    "message_safe": "检测到登录窗口验证码",           // 白名单安全文案，禁止自由文本
    "count": 1,
    "context": {
      "last_action": "click",                     // 仅技术上下文
      "retry_count": 0,
      "window_title_hash": "sha256_...",          // 窗口标题只给哈希
      "session_len_s": 640
    }
  }
}
```

**错误码枚举（首版）**：`AGENT_CRASH`、`WATCHDOG_RESTART`、`MODEL_TIMEOUT`、`MODEL_API_ERROR`、`VISUAL_MISJUDGE`（视觉误判）、`VLM_UNAVAILABLE`、`WECHAT_SESSION_LOST`、`WECHAT_CAPTCHA`、`WECHAT_WINDOW_MISSING`、`CONFIG_APPLY_FAIL`、`UPGRADE_FAIL`、`NETWORK_OFFLINE`。

**④ alert（告警事件：控制面规则产出 + Agent 本地产出）**

```json
{
  "event_type": "alert",
  "payload": {
    "alert_id": "uuid",
    "rule_id": "uuid",
    "severity": "critical|major|minor|info",
    "category": "offline|degraded|resource|model|security",
    "title_safe": "Agent 离线超过 15 分钟",
    "detail_safe": "site=site_9x1 agent=ag_5ab last_seen=2026-08-20T09:45Z",
    "state": "firing|resolved",                   // 恢复后自动发 resolved 消除告警
    "ack_status": "unacked|acked|closed"
  }
}
```

### 2.4 Agent 侧遥测管线（脱敏在源头）

```
值守机内部：聊天数据/截图 ——绝不外传——
  │
  ├─ 用量计数器（会话/消息/接管/token/成本）──▶ 10min 聚合桶
  ├─ 错误事件（异常捕获/看门狗/模型超时/视觉误判）──▶ 立即脱敏
  └─ 心跳采样（进程/资源/微信状态/版本）
       │
       ▼
  脱敏处理器（PrivGen）
     · 正则 + 本地模型双保险打码：手机号/身份证/银行卡/地址/邮箱
     · message_safe 白名单：只允许预置安全文案，禁自由文本
     · 敏感标识哈希：machine_id / window_title / 账号 ID 全部 HMAC
     · 截图默认不落盘、不上行（对齐 10 分卷 3.3）
       │
       ▼
  离线缓冲队列（持久化，重放打标记）──▶ mTLS 上行
```

## 3. 管理后台功能清单（决策者 demo 第一眼）

> 设计目标是「打开总后台 = 一眼看清全国 50~500 台值守机是否都在干活」，并按「总览 → 下钻 → 处置」三步走。

### 3.1 全局舰队视图（Fleet View）——第一屏

- 顶部 KPI：总实例数 / 在线 / 离线 / 降级 / 待升级 / 今日告警未处理。
- 按客户（租户）分组列表：每租户一卡片，显示实例数、健康状态、近 7 天可用率、最近告警。
- 单租户下钻：该客户每台值守机（site/agent）在线状态、Agent 版本、VLM/LLM 模型、微信登录态、last_seen、CPU/内存。
- 拓扑色板：绿=在线健康 / 黄=降级（degraded）/ 红=离线 / 灰=长期无数据（如客户断电关机）。
- 可用率口径（SLA 依据）：`(值守时段总时长 − 离线/降级时长) / 值守时段总时长`，按月出报表（§3.1 → N2 SLA 月度报告）。

### 3.2 单客户用量看板（Usage Dashboard）

- 时间序列：会话量 / 消息量 / 自动回复量 / 人工接管次数 / VLM 操作次数（日/周/月）。
- 成本与性能：LLM token 用量、API 成本（元）、平均响应时长、p95 响应时长、模型超时率。
- 转人工率 = 接管次数 / 会话数；接管后满意度（若客户开了满意度调研）。
- 计量计费联动：用量 vs License 配额（为 S3 用量计量 / 增购坐席铺路）。

### 3.3 错误流（Error Stream，实时）

- 浏览器 SSE（Server-Sent Events）实时推送 error 事件，延迟 < 3s。
- 过滤：按租户 / 严重度 / error_code / component / Agent 版本。
- 逐条展开：事件详情（脱敏后字段 + stack_hash 关联聚合）、同一 code 的历史频率、关联告警。
- 导出：CSV/PDF（带水印 + 导出人留痕，对齐 G4）。

### 3.4 告警规则中心（Alert Rules）

- **内置规则模板**（开箱即用，可按租户覆盖）：
  | 规则 | 触发 | 默认动作 |
  |---|---|---|
  | Agent 离线 | last_seen > 15min | 关键告警 → 钉钉/企微/飞书 + 短信(可选) |
  | 微信会话丢失 | WECHAT_SESSION_LOST / CAPTCHA | 关键告警 → 机器人 + 后台 |
  | 模型超时率 | 10min 内 timeout ≥ 5% 或连续 N 次 | 中告警 |
  | 视觉误判率 | 10min 内 VISUAL_MISJUDGE ≥ 阈值 | 中告警 |
  | 资源水位 | CPU/内存 ≥ 85% 持续 5min | 提示 → 建议扩容 |
  | API 成本突增 | 单日成本环比 +80% | 中告警（防 token 成本失控，对齐 00 总纲风险） |
  | 崩溃频率 | 1h 内 AGENT_CRASH ≥ 3 次 | 关键告警 → 触发版本回滚评估 |
- **告警治理**：ack / close / 指派处理人；告警关联 Agent 与租户，恢复自动 resolved；防抖（同一事件 30min 内不重复轰炸）。
- **告警通道**：DingTalk / WeCom / Feishu 机器人 webhook（客户自配）+ 后台告警中心 + 可选短信（关键告警）。

### 3.5 审计日志查询（Audit Log）

- 覆盖：登录会话、后台操作、配置变更、License 激活/续费、导出行为、告警处置。
- append-only 哈希链（前条哈希 + 时间戳 + 随机数），只读存储，防篡改。
- 查询：按时间 / 操作者 / 租户 / 动作类型；导出 PDF/CSV ≤ 60s，带水印。
- 双档导出：脱敏导出（默认）/ 明文导出（仅平台高权限 + 留痕）。对齐 G4 / 10 分卷 3.3。

### 3.6 配置模板下发（Config Template Push）

- 模板层级：**全局模板 → 租户模板 → 站点/Agent 覆盖**（三层继承 + 覆盖，对齐 G2「账号级配置继承」）。
- 模板内容：人设、知识库版本、模型路由、接管阈值、情绪/风险阈值、话术版本、值守时段。
- 配置版本化：每次编辑生成 revision；发布走「审批 → 灰度（先发 1 台试点 → 按比例）→ 全量」；可回滚到任一 revision。
- 生效机制：心跳捎带 `config_update` → Agent 拉取新 revision → 应用 → 自检 → 回报 apply_result（成功/失败回滚）。

## 4. 多租户隔离

### 4.1 租户 ID 全链路

`tenant_id` 贯穿：Agent 证书（subject）→ 请求头 → Kafka 消息 key/header → 消费侧上下文 → 存储每张表的强制列 → 告警/审计记录 → 学习仓（聚合到群组后**移除 tenant 维度**）。

### 4.2 独立数据边界

- **逻辑隔离（主形态，SaaS 多租户）**：单套 PostgreSQL，**所有业务表带 `tenant_id` 列 + 行级安全策略（Row-Level Security）**。API/服务层每次查询由框架强制注入 `WHERE tenant_id = current_setting('app.tenant_id')`，RLS 作为第二道防线（即使 SQL 漏写也查不到别家）。
- **物理隔离（可选，高合规租户）**：可租户独立 schema 或独立实例；升级到「私有化控制面」形态（§5.2）。
- **时序隔离**：TDengine 用「超表（supertable）+ 子表按 tenant 分」；查询天然带 tenant 过滤。
- **对象存储隔离**：路径前缀 `oss://telemetry/{tenant_id}/{date}/` + bucket policy 按 tenant 前缀授权。

### 4.3 跨租户禁止的工程保障

1. RLS 强制 + 服务层租户上下文（双保险）。
2. API 网关统一解析 Token → 注入 `X-Tenant-Id`，业务层不信任客户端传入的租户字段。
3. CI 中跑「租户隔离自测」用例：A 租户管理员 token 查 B 租户资源必须 404/403（对齐 10 分卷 3.2 的「隔离验证」）。
4. 列表/导出接口强制租户过滤；无「跨租户导出」能力。
5. 平台超级管理员跨租户访问必须显式「以某租户身份进入」并留审计（支持场景：运维排障）。

### 4.4 与 10 合规分卷「元数据边界」对齐

| 10 分卷要求 | 本架构落点 |
|---|---|
| 云侧只承载授权/License/升级/告警元数据 | §2 遥测四类事件只含元数据，不含聊天内容/PII |
| 不汇聚企业客户聊天数据 | §2.4 Agent 侧脱敏 + Schema 白名单，聊天/截图本地留存不落云 |
| 数据归属、备份、销毁有明确边界 | 租户数据生命周期管理：到期/退订 → 租户归档 → 30 天后删除并提供删除证明（对齐 PIPL 21 条受托义务） |
| 禁止跨租户查询 | §4.3 双保险 + 隔离自测 |
| 合同终止删除/返还并提供删除证明 | 控制面提供「一键导出 + 一键销毁 + 删除证明」能力 |

## 5. 部署形态：一套代码，两种形态

### 5.1 SaaS 控制面（主形态）

- 我们托管（云服务器/容器平台），多租户模式（§4），面向 50+ 订阅客户。
- 面向 90 天：单栈容器（docker compose 起步）即可承载 50 实例；500+ 走 §6.5 阶段演进。
- 客户零运维：值守机装机即接入，无需部署任何服务端。

### 5.2 私有化控制面（高合规客户可选）

- 场景：政务/金融/医美等强合规客户，要求管理面数据也留在自己内网。
- 形态：同一份代码库打出的**私有化包**（docker compose / Helm），运行在客户内网服务器，**单租户模式**。
- 差异点仅来自配置与 feature flag，不 fork 代码：
  - `DEPLOYMENT_MODE=saas|onprem`
  - `TENANT_MODE=multi|single`（single 时 RLS 降级为单一租户，无隔离开销）
  - `LEARNING_UPLINK=enabled|disabled`（默认 disabled；启用须客户书面同意，且只传 §9 的匿名聚合）
  - 内置存储：捆绑 PostgreSQL + TDengine（可选单实例轻量模式，或退化为「PG 存心跳近况 + 文件日志」）。
- **升级通道**：私有化控制面本身也走「版本发布 + 客户侧手动/定时拉取」，与 Agent OTA（§8）同机制。

### 5.3 一套代码两形态复用

```
monorepo/  (控制面代码库)
├── core/           # 与部署形态无关的核心库：事件模型、脱敏规则、租户上下文、规则引擎
├── services/
│   ├── gateway/    # Agent 接入网关（mTLS）
│   ├── ingest/     # Kafka 消费 + 写存储
│   ├── alert/      # 告警引擎
│   ├── api/        # 管理后台 REST API
│   ├── ota/        # 版本管理 + 灰度 + 升级包签名
│   ├── learning/   # 聚合 job + 学习仓只读 API
│   └── license/    # License 服务
├── web/            # React 管理后台前端
├── deploy/
│   ├── saas/       # 多租户编排
│   └── onprem/     # 私有化包（同一镜像，不同 env）
└── agent-sdk/      # Agent 内嵌遥测 SDK（心跳/脱敏/OTA 客户端）
```

## 6. 扩展性：50 → 500+ 实例

### 6.1 容量估算（500 实例口径）

| 指标 | 估算 | 说明 |
|---|---|---|
| 心跳 | 720,000 条/日（平均 8.3/s，峰值 ~25/s），单条约 400B | 1 次/60s × 500 |
| 用量事件 | ~1,000,000 条/日（平均 11.6/s，峰值 ~35/s），单条约 800B | 每实例 ~2,000 条/日 |
| 错误事件 | ~10,000 条/日（峰值可冲高），单条约 1KB | 每实例 ~20 条/日，突发拉高 |
| **合计入站** | **均值 ~20/s，峰值 ~300/s** | Kafka 单 topic 数分区即可，按 site hash 分区 |
| 时序存储 | 心跳 ~216MB/日 → TDengine 保留 30 天 ≈ 6.5GB（自动降采样后更小） | 保留策略自动滚动 |
| 关系存储 | 用量日桶 500 条/日 + 审计 ~5K 条/日 + 元数据 → < 10GB/年 | PG 完全无压力 |
| 对象归档 | usage/error 原始 ~1GB/日 × 90 天 ≈ 90GB | 学习仓 + 审计溯源 |

> 结论：500 实例的遥测吞吐对「Kafka + PG + TDengine」是**微不足道**的量级。真正要防的是**存储无界增长**，所以设计重点在「保留策略 + 降采样 + 聚合桶 + 对象归档」，而非吞吐本身。

### 6.2 消息队列选型

- **选型：Apache Kafka（托管优先：云 Kafka / 自建 KRaft 模式）**。
- 理由：① 遥测需要**持久化 + 重放**（消费挂了不丢数据，学习/告警可回放）；② 天然支持流式聚合与多消费者（告警、存储、学习三个消费者互不阻塞）；③ 500 实例阶段单 topic 几分区即可，未来到数千实例也无需换技术。
- **阶段 A（50 实例）替代**：可先用 Redis Streams 或直接网关写库，但**保留 Kafka 的 topic 语义**（`telemetry.*`）以便无缝迁移——90 天不强制上 Kafka，但模型（topic 分区、幂等去重）必须定好。
- 分区策略：`telemetry.heartbeat` 按 `site_id` hash；`telemetry.usage` 按 `tenant_id`；`telemetry.error` 全局（量小，便于全局错误流）。

### 6.3 存储选型

| 用途 | 选型 | 理由 |
|---|---|---|
| 租户/License/配置/审计 | **PostgreSQL 16** | 关系型 + RLS 天然支撑多租户；审计 append-only 哈希链表；单库即可撑 500 租户 |
| 心跳/健康时序 | **TDengine** | 国产、SQL 化、超表按设备建模、自动降采样 + 保留策略、低运维；契合「设备遥测」场景 |
| 原始遥测归档 | **对象存储（阿里云 OSS / 腾讯云 COS / 私有 MinIO）** | 低成本、生命周期管理（90d 自动过期）；学习仓与审计溯源读取 |
| 在线状态/限流/SSE 分发 | **Redis** | 会话、在线状态 TTL、告警防抖、SSE 订阅分发 |
| 控制面自身可观测 | **Prometheus + Grafana + 云告警** | 控制面自己的健康监控（自举 dogfood 自家值守机理念） |

> 权衡：暂不引入 OpenSearch/Elasticsearch（500 实例的错误/日志量不足以支撑其运维成本）；若未来审计/日志全文本检索需求增大，再从 PG 演进（数据可导出迁移）。

### 6.4 告警引擎

- **规则评估**：轻量规则引擎（Kafka 消费 → 滑动窗口计数 + 阈值），50–500 实例用 Go 服务即可，无需重型流计算框架（暂不引 Flink）。
- **离线检测**（最关键的告警）：不依赖事件流，而是对 TDengine/Redis 的 `last_seen` 索引做**每 1 分钟扫描**，超过阈值（默认 15min，SLA G7 依据）→ 触发 `offline` 告警；恢复后自动 `resolved`。500 实例的 last_seen 扫描是毫秒级。
- **防抖/升级**：同一规则 30min 防抖；`minor → major` 升级；告警降噪（维护窗口跳过）。
- **送达**：告警中心 + DingTalk/WeCom/Feishu webhook（客户自配）+ 可选短信。

### 6.5 分阶段演进路径（与 90 天对齐）

```
阶段 A（90 天内，50 实例）——轻量可交付
  · docker compose 单栈：Nginx + Go API + PostgreSQL + Redis
  · 心跳直接写 PG/TDengine（单机 TDengine 或先 PG 存近况）
  · 告警用定时扫描器；错误流用 SSE 直连
  · 不上 Kafka / 不拆微服务 → 满足「不做重多租户云版」CEO 定向
  · 但数据模型/租户隔离/topic 语义按 B 设计，避免返工

阶段 B（100–200 实例）
  · 引入 Kafka telemetry.* 做解耦与重放；告警引擎独立服务
  · 引入 TDengine 正式承载时序；原始遥测归档对象存储
  · 错误流改走 Kafka → SSE 适配器

阶段 C（500+ 实例）
  · 网关水平扩容 + mTLS 证书批量管理（自动轮换）
  · Kafka 分区扩展 + 消费者组横向扩；TDengine 集群
  · 聚合 job 定时产出学习仓；对象存储生命周期管理
  · 若出现全文检索需求，再评估 OpenSearch
```

## 7. 安全

### 7.1 控制面登录 / RBAC / 审计

- **认证**：OIDC/SAML（自建账号库起步，可对接客户企业 SSO）+ 强制 MFA（管理员）。
- **角色**：
  | 角色 | 范围 | 能力 |
  |---|---|---|
  | 平台超管 | 全平台 | 运维排障（显式切换租户 + 审计）、License 管理、版本发布 |
  | 客户管理员 | 本租户 | 管理 Agent/配置/告警/看板，本租户全部权限 |
  | 坐席/操作员 | 本租户 | 看板、接管、告警 ack |
  | 只读审计员 | 本租户或全平台 | 只读 + 审计导出（脱敏档） |
- **会话**：JWT（短期）+ Refresh；离职回收（对齐 G8「员工离职回收」）。
- **审计**：所有登录/操作/导出/跨租户访问 append-only 留痕（§3.5）。

### 7.2 Agent ↔ 控制面双向认证

- **双向 mTLS**：Agent 装机时签发**客户端证书**（内部 CA），证书 subject 绑定 `tenant_id + site_id + agent_id`；控制面网关校验证书吊销列表（CRL/OCSP）。
- **站点 Token**：租户级长效 Token（哈希后存储），用于 API 请求鉴权 + License 激活绑定。
- **证书生命周期**：有效期（如 180 天）+ **自动轮换**（心跳响应捎带「证书将过期」→ Agent 重新签发）；支持手动吊销（客户退订/实例废弃）。
- **证书私钥**：Agent 本地加密存储（DPAPI / 本地密钥文件），不落盘明文。

### 7.3 密钥管理

- 控制面侧：云 KMS / Vault 托管——License 签名私钥、内部 CA、JWT 签名密钥、对象存储凭证。私钥不出 KMS。
- Agent 侧：API Key（LLM/VLM）加密存储 + 密钥托管（对齐 G8：SQLite 加密 + Key 托管），密钥与数据分离、可轮换。
- 轮换策略：KMS 密钥按周期轮换；泄露即吊销（提供「全局吊销某租户密钥」能力）。

### 7.4 遥测脱敏

- **源头脱敏**（§2.4）：正则 + 本地模型双保险，PII 打码后才入队上行。
- **Schema 白名单**：Agent 只按 schema 输出字段，无自由文本；`message_safe` 从预置安全文案字典取值。
- **哈希标识**：machine_id / window_title / profile 均 HMAC，不可逆。
- **截图/聊天内容零上行**：控制面代码层面没有接收聊天数据的字段——即便 Agent 被攻破，云侧也「接不住」客户数据（安全边界 + 合规边界双赢）。
- **传输与存储**：全链路 TLS；对象归档静态加密（SSE-KMS）；审计导出双档（§3.5）。

## 8. 升级下发（OTA）

### 8.1 版本管理

- **语义化版本** semver + 通道（`stable` / `beta`）。
- **发布物**：升级包（压缩包 + 元数据 + **Ed25519 签名** + SHA256 校验和），上传对象存储。
- **兼容矩阵**：`release → 允许的 agent_version 范围`；`agent_version → 最低控制面 API 版本`。控制面维护「最新稳定版 / 最低支持版 / 阻断版」三态。
- **强制/可选**：安全补丁=强制；功能升级=可选（客户后台可设自动或手动）。

### 8.2 灰度发布

- **阶梯发布**：单台冒烟（选定 site）→ 5% → 25% → 50% → 100%，每级一个**健康门禁**。
- **健康门禁指标**（自动暂停）：新版本崩溃率、错误率、回滚率、离线率、模型超时率——任一超阈值即**自动暂停**并通知运维。
- **租户级策略**：可按租户设「锁定版本」（如客户验收期锁版本）或「跟进通道」（stable/beta）。
- **发布窗口**：默认业务低峰（如 02:00–06:00 客户时区），可配置。

### 8.3 回滚

- **本地双份**：Agent 保留上一版本 bundle；新版本启动后进入 10 分钟自检期，失败（崩溃/看门狗/自检失败）→ **自动回滚**上一版本。
- **控制面强制回滚**：发布版本被标记 `blocked` → 心跳捎带 `upgrade` 指向上一版本 → Agent 拉取回滚。
- **回滚率指标**进发布健康门禁（回滚率过高 → 停发并封版）。

### 8.4 离线客户升级策略

- **断网/关机**：升级命令在控制面标记 `pending`；Agent 恢复心跳时收到捎带命令 → 拉取安装（§1.2 的 long-poll 模式天然支持离线延迟升级）。
- **长期离线（> 版本支持窗口）**：Agent 心跳携带版本 → 控制面提示「低于最低支持版」→ 客户后台告警；Agent 恢复后按强制通道补丁。
- **完全隔离网络（air-gapped）**：支持**离线升级包**下载（带签名 + 校验和），客户 U 盘/内部渠道分发，Agent 手动导入安装。
- **升级失败兜底**：下载失败重试 + 指数退避；签名校验失败拒绝安装；连续失败告警。

## 9. 与「沉淀学习」的接口

> 目标：让 AI 工程师在「看不到任何客户原文」的前提下，获得跨实例的模式洞察，反哺默认配置、路由策略、看门狗阈值与模型选型。

### 9.1 聚合层设计（只给聚合，不给原文）

- **输入**：对象存储里的原始遥测（usage/error，已脱敏、无聊天内容）。
- **每日聚合 job** 产出**群组级聚合**（按匿名维度：agent_version × 模型 × 行业标签 × 区域 × 日期），写入独立「学习仓」：
  - 错误分布：`error_code × component × agent_version` 计数、占比、环比。
  - 成本与性能：`llm_model × 区域` 的 p50/p95 响应时长、token 成本/条、超时率。
  - 视觉误判率：`VISUAL_MISJUDGE × 场景` 频率 → 反哺看门狗/接管阈值。
  - 版本健康：各 agent_version 的崩溃率/回滚率/错误率 → 指导灰度发布节奏。
  - 配置效果：模板 revision 前后「转人工率 / 接管率 / 满意度」的变化（同一客户的配置前 vs 配置后，聚合到群组）。
- **k-匿名门槛**：**参与聚合的实例数 ≥ 10 才出数**，不足则该群组抑制；敏感指标加噪声（差分隐私化处理）。
- **移除租户维度**：聚合表**没有 tenant_id**（只有行业/区域等匿名标签），从数据层杜绝「用学习仓反查某客户」。

### 9.2 学习数据集 API

- 只读 API（内部，AI 工程师角色 + 独立 API Key + IP 白名单），支持按维度切片查询聚合。
- 输出格式：Parquet/CSV 数据集（可进模型 eval / 分析 notebook）。
- 消费方：AI 工程师（调默认 prompt、路由、阈值）→ 产出**新配置模板默认值** → 回到 §3.6 配置模板下发闭环。

### 9.3 合规边界

- 学习仓只存聚合，不存原文；与生产遥测存储**物理/逻辑隔离**。
- 私有化控制面的学习回传为 **opt-in**，须客户书面同意，且只传 §9.1 聚合（可关闭）。
- 对外文档（安全白皮书）明示：「跨实例学习仅基于匿名统计，不涉及任何客户内容」。

## 10. 技术选型总表

| 层 | 选型 | 备选 | 权衡要点 |
|---|---|---|---|
| Agent 接入网关 | Go（net/http + mTLS） | Node/NestJS | Go 并发与 TLS 卸载稳妥；网关是唯一外露面 |
| 管理后台 API | Go（Gin/Echo） | NestJS | 与网关同语言减少心智；前端 TS 复用受控 |
| 管理后台前端 | React + Vite + TS + ECharts | Vue3 + Element Plus | 图表/SSE/复杂表格生态；中国客户外包环境 Vue 更易招人，可按团队技能换 |
| 消息队列 | Apache Kafka（云托管/KRaft） | Redis Streams（阶段A）/ Pulsar | Kafka 持久+重放+多消费者；阶段A可退化为 Redis Streams，topic 语义保留 |
| 关系存储 | PostgreSQL 16 + RLS | 云 RDS PG | RLS 是租户隔离核心；单库撑 500 租户 |
| 时序存储 | TDengine | InfluxDB / TimescaleDB | 国产、超表建模、降采样+保留策略，低运维 |
| 对象存储 | 阿里云 OSS / 腾讯云 COS / MinIO | S3 全兼容 | 归档 + 升级包 + 审计导出 |
| 缓存/在线状态 | Redis | — | 会话/在线/防抖/SSE 分发 |
| 告警引擎 | Go 自研轻量规则 + last_seen 扫描 | Flink（后期可选） | 500 实例无需重型流计算 |
| 认证 | OIDC/SAML + JWT + MFA | — | 可对接企业 SSO |
| 密钥管理 | 云 KMS / Vault | — | License 私钥/CA/JWT 不出 KMS |
| 控制面可观测 | Prometheus + Grafana | 云监控 | 自举 dogfood 值守机理念 |

**技术栈演进承诺**：阶段 A 是「同一架构的精简实现」，不是临时方案；数据模型、topic 语义、租户隔离、OTA 协议在阶段 A 就按 500+ 定义，B/C 只做「扩容 + 加 Kafka + 加归档」，不做数据模型重构。

## 12. ADR 记录（关键决策）

### ADR-001：控制面只收元数据，不设聊天内容通道
- **状态**：已接受（合规硬约束）。
- **背景**：10 分卷 3.1 数据边界铁律；「RichCat 不是个人信息处理者」是商业主张的事实基础。
- **决策**：遥测 Schema 只含四类元数据事件；Agent 侧脱敏 + 白名单；云侧无接收聊天/截图的字段。
- **备选**：云侧集中存储聊天（否决：PIPL 受托责任 + 客户法务一票否决风险）。
- **影响**：沉淀学习只能用聚合（§9）；管理后台看不到聊天原文（符合产品定位：客户自己数据自留）。

### ADR-002：租户隔离用「PostgreSQL RLS」而非「每租户独立实例」
- **状态**：已接受。
- **背景**：50 家起步，运维单点；10 分卷 3.2 允许逻辑隔离。
- **决策**：共享 PG + `tenant_id` 强制列 + RLS；高合规租户升级独立 schema/私有化。
- **影响**：运维成本低；牺牲「物理隔离」的极端隔离度（用「私有化控制面」形态补偿）。

### ADR-003：下行用「心跳捎带命令」而非「服务端长连接」
- **状态**：已接受。
- **背景**：值守机在客户 NAT 后，主动长连接复杂且防火墙易断。
- **决策**：配置/升级/重启命令搭在心跳响应中（long-poll）；WebSocket 仅作紧急通道可选。
- **影响**：命令送达延迟 ≤ 心跳周期（60s，可降级 30s），满足「配置 5 分钟生效」；离线自动变「待升级」语义，天然支持离线升级。

### ADR-004：阶段 A 不上 Kafka，但保留 topic 语义
- **状态**：已接受（CEO 定向「不做重多租户云版」）。
- **背景**：90 天 50 实例量极小；上 Kafka 增加运维负担。
- **决策**：阶段 A 用网关直写库 + 可选 Redis Streams；事件模型按 `telemetry.*` topic 语义设计。
- **影响**：阶段 B 迁移低成本；避免「先 Redis 后改 Kafka 的返工」。

### ADR-005：时序存储选 TDengine
- **状态**：已接受。
- **背景**：500+ 实例心跳/健康指标是典型设备时序；团队小需低运维。
- **决策**：TDengine 超表建模 + 自动降采样 + 保留策略；心跳即写入。
- **影响**：舰队视图/可用率报表查询简单；国产化利于私有化合规客户（信创友好）。
